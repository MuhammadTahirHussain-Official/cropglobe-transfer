# CropGlobe Level 1 v3.4 - change log (since v3.3)

**Triggered by your Colab run.** Observed in Colab (output pasted by you; not run by me): Part A passed; Part B passed against the REAL authors' `remap_prediction` (existing_release identical to the released function on 5,000 random predictions per target; paper_text_v3 differs on ARG only, review_targetmap on FRA only; probes changed the input for ARG, CHN, AUS); the data load then STOPPED in `build_usa_meta` (V33-06 gate): three row orderings reproduce the label sequence, lifts 95.74x / 93.07x / 95.78x, the two alternatives differ from the chosen one on 17.4% and 15.4% of rows.

What I verified about that stop:
- **The STOP is correct, not a false alarm.** The dataset card (huggingface.co/datasets/x-ytong/CropGlobe) documents no USA row order, sample ids, coordinates or state information, so there is no independent identifier; the alignment rests on a feature heuristic.
- **17.4% is the wheat share of the USA set** (23,226 / 133,279 = 17.43%). The disputed rows are therefore very probably exactly the wheat rows, i.e. the order of the spring- vs winter-wheat files (tokens `springwheat` / `winterwheat`). This is an inference from the arithmetic; the file list was not visible to me.
- **The lift heuristic is blind to that.** It averages over the 7 crops; 6 are identical in every candidate, so they dilute the one crop that differs. In addition the chosen ordering's lift (95.7x) was computed with one random permutation stream and the alternatives' lift (102.0x) with another (n_perm=8), so the numbers compared in the 15% test were not paired. (The unpaired comparison pre-dates v3.3; v3.3 made it consequential by turning the warning into a STOP.)
- Why it matters: wheat is a fixed key crop for FRA (15%) and part of the natural remainder everywhere, so wheat rows with the wrong state would change which states can supply what.
